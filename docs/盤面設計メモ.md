## 3. B-4 の確定 — ポジションチェンジ / フォーメーションチェンジ（決定 D74）

### 3-1. 条文

| 条 | 本文 |
|---|---|
| 11.10.1 | ポジションチェンジするとは、そのメンバーを**今いるエリア以外のエリア**に移動させることである |
| 11.10.2 | 移動させた先のエリアに**すでにメンバーがいる場合**、移動先にいるメンバーは、移動してきたメンバーが**いたエリアに移動する** |
| 11.11.1 | フォーメーションチェンジするとは、**ステージにいるすべてのメンバー**を、それぞれ好きなエリアに移動させることである |
| 11.11.2 | この効果で **1 つのエリアに 2 人以上**のメンバーを移動させることは**できない** |

★整合性チェック B-4 が言うとおり、これらは `【】` のキーワード能力ではなく**効果テキスト中の動詞**である。
**いつ起きるかを決めるのは効果**であり、アプリは読まない（D-A）。**プレイヤーが宣言して押す。**

### 3-2. 置くか、置かないか — **置く**

置かない場合、11.11.1（全員の再配置）は**ドラッグを 3〜5 回**行うことになる。
そのあいだ 1 エリアに 2 人並ぶ中間状態が続き、**うっかり「整理」を押すと 10.4 の重複メンバー処理で
片方が控え室へ行って戻せない。**

★**これは効果の自動処理ではない。** 移動先も枚数もプレイヤーが指定する。
アプリがやるのは**複数の移動をまとめて 1 回で適用すること**だけであり、
CLAUDE.md §1（D-A）の許す「移動」の範囲に収まる。

### 3-3. `GameAction` への写像 — ★`loveca_core` の変更は要らない

| 操作 | 写像 |
|---|---|
| ポジションチェンジ（移動先が空） | `MoveMemberBetweenAreas` × 1 |
| ポジションチェンジ（11.10.2 の入れ替え） | `MoveMemberBetweenAreas` × 2 |
| フォーメーションチェンジ（11.11.1） | `MoveMemberBetweenAreas` × N |

成立の根拠 3 つ。

1. **4.5.5.3（下に重ねられたカードも同時に移動）を `_moveMemberBetweenAreas` が既に満たす**
   （`reduce.dart:351-379` がスタックごと移す）。★重ね置きのあるメンバーでも壊れない。
2. **途中で 1 エリアに 2 人並ぶ中間状態は正規である**
   （`member_area.dart:71-73` / 10.1.2 によりルール処理はチェックタイミングでのみ走る）。
   したがって**任意の置換に到達できる** —— 例: L→C→R→L の巡回は
   「L→C（C が 2 人）→ 元 C を R へ（R が 2 人）→ 元 R を L へ」で終端は各 1 人。
3. `MemberArea.stacks` の**リスト順は配置順**（10.4.1 の「最も後から置かれた」）であり、
   `MoveMemberBetweenAreas` は移動先の**末尾**に積む。移動したメンバーが最も後から置かれた扱いになるのは正しい。
   ★**このリストを並べ替える操作は作らない**（`member_area.dart:99-102` の規約）。

★★**守ること 2 つ**★★

- **合成の途中で `Tidy` を挟まない。** 挟むと 10.4 が走って中間状態が壊れる
- **1 undo にまとめる**（§8-2）。`GameSession.apply` を N 回呼ぶと undo が N 回要る

### 3-4. ★ 制約はコマンドの中だけに置く

11.10.2 の入れ替えも 11.11.2 の「1 エリアに 2 人以上不可」も、**その効果の中での制約**であって
盤面の不変条件ではない。

★★**素のドラッグに課してはいけない。**★★
課すと 4.5.5 / 10.4 の中間状態を作れなくなり、
**「上にメンバーが居ない孤児カード」「2 人並んだエリア」を手で再現できなくなる。**
それは `MemberArea` が型で表現できるようにした状態そのもの（`member_area.dart:52-75`）であり、
サンドボックスから機能を削ることになる。

| 経路 | 11.11.2 を課すか |
|---|---|
| 素のドラッグ（`MoveMemberBetweenAreas` 単発） | ★**課さない** |
| ポジション / フォーメーションチェンジのコマンド | **課す**（コマンドの中の割り当て UI で） |

### 3-5. 【要確認】1 エリアに 2 人以上いるとき

11.10.2 は移動先のメンバーを**単数**で書いており（「移動先にいるメンバーは」）、
**2 人以上いる場合を定めていない。** 11.11.2 も同じで、
既に 2 人並んでいるエリアがあると「すべてのメンバーを 1 エリア 1 人ずつ」が**不可能**になる。

→ ★**推測で埋めない。** どちらかのエリアに 2 人以上いる間は**コマンドを無効にし、理由を出す**
（「先に整理（10.4）してください」）。★**黙って効かないボタンにしない。**
公式 Q&A で裏が取れたら再確認する。

## 4. 盤面のレイアウト（決定 D75）

### 4-1. 置き場の数え

★**根拠のない数を書かない**（D-B）ので、条文から数え直す。

総合ルール 4 章が定義する領域は **11 種**（4.4〜4.14 が 1 節 1 領域。`zone.dart` の enum 値 11 と一致）。
このうち、

- **ステージ（4.4）は実体を持たない。**4.4.1「プレイヤーのメンバーエリアを**統合した**領域です」
- **解決領域（4.14）だけが共有。**4.14.1「両プレイヤーが共有して使用する領域が **1 つだけ**存在します」
- **メンバーエリア（4.5）は 3 スロット。**4.5.2 / 4.5.2.1（左サイド / センター / 右サイド）

→ **盤面に描く置き場**

| 区分 | 数 | 内訳 |
|---|---:|---|
| プレイヤーごと | **11** | メンバーエリア 3（4.5.2.1）/ ライブカード置き場（4.6）/ 成功ライブカード置き場（4.10）/ エネルギー置き場（4.7）/ エネルギーデッキ置き場（4.9）/ メインデッキ置き場（4.8）/ 手札（4.11）/ 控え室（4.12）/ 除外領域（4.13） |
| 共有 | **1** | 解決領域（4.14.1） |
| ★ルール外 | **2** | 6.2.1.6 の脇置き / フリーエリア（`OutOfRuleZone`） |

★**ルール外の 2 つを 4 章の領域と同じ見た目にしない。**
`Zone` と `OutOfRuleZone` を別の型に分けた 3a-1 の拘束（`zone.dart:133-143`）を UI でも守る。
**盤の外**に畳んで置き、見出しで「ルールの領域ではありません」と断る。

### 4-2. ★ 4.5.7.1 が鏡像配置を要求している

> センターエリアは他プレイヤーのセンターエリアが、

## 8. 巻き戻し（決定 D78）

### 8-1. `undo` と `undoStep` を別のボタンで出す

`GameSession` が 2 つを持つ（`history.dart:109-139`）。**着地先が違うので同じボタンにしない。**

| ボタン | 呼ぶもの | 着地先 |
|---|---|---|
| **1 つ戻す** | `undo()` | 直前の 1 操作を取り消す |
| **1 ステップ戻す** | `undoStep()` | ①そのステップ内で操作していたなら**そのステップの入口** ②入った直後なら**1 つ前のステップ** |

★**押す前に着地先を出す。** `history.last?.cursor` から
「エネルギーフェイズ **7.5.2** の入口へ戻ります」のように**条番号つきで**出す。
D31 が「フェイズを 1 つ戻す」だったものをステップ単位に読み替えてある（`docs/PhaseEngine設計メモ.md` §6）以上、
**どこへ着地するかが見えないと使えない。**

★**`canUndo` が false のときはボタンを消さず、無効にして理由を出す。**
黙って効かないボタンを作らない（このリポジトリで一貫している方針）。

★**`GameHistory.maxDepth` は 512 で、超えると古いものが黙って捨てられる**（`history.dart:67-75`）。
`depth == maxDepth` を検出して「これより前へは戻せません」と出す。**捨てたことを黙らない。**

### 8-2. 合成コマンドは 1 record にする

`GameSession.apply` は「現在の状態を履歴に積んでから `reduce`」する（`reduce.dart:149-152`）ので、
N 回呼ぶと**履歴が N 件積まれ、undo が N 回要る。**
フォーメーションチェンジ（§3）やライブカードセット（§7-3）では**1 操作として戻せなければ困る。**

→ **`reduce` を N 回回して合成状態を作り、`GameSession.record` を 1 回だけ呼ぶ。**

```dart
var s = session.state;
for (final a in actions) { s = reduce(s, a, context: ctx); }
session = session.record(s);   // ★履歴 1 件
```

★`record` は公開 API なので **`loveca_core` の変更は要らない。**
★D36 がスナップショット方式（アクションログではない）を採ったので、
履歴 1 件とアクション N 件が対応しないことは設計と矛盾しない。

### 8-3. ★★ 巻き戻しても乱数は戻らない ★★

`SeededRng` は内部状態を持ち、`GameHistory` は `GameState` しか持たない。
`ReduceContext` の `rng` は UI が作って持ち回る。
→ **undo で盤面を戻しても、乱数の消費位置は戻らない。**
**戻して引き直すと違うカードが出る。**

#### 採用: 明示するだけ（張り直さない）

| # | 根拠 |
|---|---|
| 1 | ★**`reduce` の再現性の契約は「アクション列」に対するもので、undo はアクションではない**（`game_action.dart:21-25`「undo / undoStep はここに入れない」）。契約は破れていない |
| 2 | 消費数を履歴と並行して持つと**二重管理**になる。D49 が案A（写像をメモリに保持）を却下したのと、D-11（並び順が経路で違う）と同じ型の悪さ |
| 3 | ★D-A のサンドボックスでは、そもそも任意のカードを任意の場所へ動かせる。**undo で引き直せることは新しい能力ではない** |

#### ★ 根拠 1 を実測で確かめた（2026-08-24）

★★**「成立するはず」と書くのと「成立する」を示すのは別である（D-10）。**★★
検証スクリプトを `loveca-core` の `package_config.json` を指して走らせた
（★スクリプトはリポジトリの外に置いた。`loveca_core` は 1 文字も変えていない）。

**まず、素朴な形は成立しない。**

```
実セッション:      s1=reduce(s0,a1) / s2=reduce(s1,a2) / undo→s1 / s3=reduce(s1,a3)
アクション列だけ:   t1=reduce(s0,a1) / t2=reduce(t1,a2) / t3=reduce(t2,a3)     → s3 ≠ t3
```

a2 の**乱数消費は残るのに状態効果は消える**という非対称があるため。

**★成立する正しい形: ログに `undo` / `undoStep` も発生順に載せる。**

|---|---|---|

| 2 | ★**対**: 同じログから `undo` を落として再生 → **一致しない** | ○（＝ ログに載せる必要があることの証明） |

**盤面セッションのログはアクションと undo を別枠で、しかし同じ列に載せなければならない。**
載せなければ再生できない。→ **`BoardSession` のログは `sealed`（`Act` / `Undo` / `UndoStep`）にする。**

★★**この 2 件の再現手段は、いまリポジトリに無い。**★★
設計のみの作業だったため、検証は**リポジトリの外の使い捨てスクリプト**で行った。
**このままだと D51 が戒めている「判断根拠が検証不能な主張になる」状態である。**

#### ★ 出し方 — 毎回出さない
