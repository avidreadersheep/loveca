### ★ D72 の詳細（2026-08-24 決定 / 未決 U11 の解消）

#### 事実（実データ全数計測）

| 種別 | thumb の寸法 | 比 (w/h) |
|---|---|---|
| メンバー | 200×279（1,036）/ 200×280（483） | 縦長 **0.717** |
| エネルギー | 200×279（484）/ 200×280（228）/ 200×273（5） | 縦長 **0.717** |
| ★**ライブ** | **200×143（290）/ 200×144（1）** | **横長 1.399** |

全部を 200:279 の箱に `BoxFit.cover` で入れていたため、ライブは
**左右 48.7% が切り落とされ、表示倍率 1.951 倍に拡大されていた**（＝ぼやけていた）。

#### ★★ なぜ D42 の再測定に当たらないか ★★

`ResizeImage` を入れると枚数上限（1000 枚）側が先に効くため、
バイト上限を 256MiB にしても載る枚数は変わらない（実測で 1000 枚 / 72.5 MiB のまま）。
**上限を触るのではなく 1 枚を小さくするのが正しい手当て。**

★`cacheWidth` は**物理ピクセル**で指定する。論理 px を渡すと DPR 倍だけ小さくデコードされ、
拡大表示になってぼやける。

★**プレースホルダは要る。** 速いスクロール（5,418 px/s）では
2,477 枚中 21〜41 枚しかデコードが間に合わない。
このときフレーム統計は綺麗なままなので、**「フレーム落ちなし」だけを見ると
「空白を高速で流しているだけ」を快適と読み違える。**

★**`precacheImage` の常時先読みは採らない。** 60 セル先読みは速いスクロールでは
実質「全件先読み」になり、RSS ピークが 141〜151 MiB から 175〜178 MiB へ増える。

#### D43: カード画像はローカルファイルから読む

配信物の画像は `loveca-data/data/dist/images/{thumb,normal,large}/{imageHash}.webp`。
`imageHash` からのファイル名組み立ては**こちらが決めた規約**なので行ってよい。

★**公式サイトの `picture` から URL を組み立ててはいけない**（CLAUDE.md §5-(3)）。
これは別の話であり、緩めない。

Phase 4 で配信経路が固まるまで、UI 側にネットワーク取得の口を作らない。
経路が 2 つあると「どちらから来た画像か」で不具合の切り分けができなくなる。

#### D44: デバウンスは 150 ms。結果上限は 2000 にして打ち切りを見せる

★**デバウンス値が打鍵間隔以下だと、検索回数は 1 回も減らないまま待ち時間だけ増える。**

打鍵 120 ms で「スクールアイドル」（8 文字）を入力した実測。

| デバウンス | 実行された検索 | 最後の打鍵から結果まで |
|---:|---:|---:|
| 0 ms | 8 回 | 24 ms |
| 100 ms | **8 回**（減っていない） | **128 ms** |
| **150 ms** | **1 回** | 179 ms |

150 ms を採るのは、日本語入力の実際の `onChanged` 間隔（ローマ字 1 文字ごと・
60〜120 ms 相当）を両方 1 回に畳めて、かつ 179 ms が
「引っかかった」と感じる 200 ms を下回るため。

★**上限は描画の都合ではない。** 1,668 刷りの描画は 4〜10 ms・予算超え 0 で、
`GridView.builder` の仮想化により件数は描画コストにほとんど効かない。
問題は**現在の既定 `limit: 500` が結果を黙って切る**こと。
実データで `ー` は 1,034 種、`ライブ` は 602 種ヒットするのに 500 で打ち切られ、
利用者にはそれが分からない。
**これは「trigram が 3 文字未満で黙って 0 件を返す」（`card_search_dao.dart` の
`CardSearchMode.likeFallback` のコメント）と同じ型の失敗である。**
上限は 2000（実データの最大 1,708 種より大きい）に上げ、
それでも切れたときは件数を画面に出す。

#### D45: drift は別 isolate で開く

| 観点 | UI isolate | **別 isolate（採用）** |
|---|---|---|
| trigram 検索 1 回 | 7.8〜9.3 ms（**速い**） | 11.0〜15.0 ms |
| コールド取り込み中に出たフレーム | **26 / 1,285 ms（約 20fps）** | **242 / 1,800 ms** |

検索 1 回だけなら UI isolate のほうが速い（isolate 間の往復が無いため）。
**決め手はコールド起動の取り込み。** 1.8 秒の取り込みが UI スレッドで走ると画面が止まる。

★**`loveca_db` は変更しない。** `LovecaDatabase(QueryExecutor)` という形で
executor を呼び出し側から受け取る設計になっているので、アプリ側で
`NativeDatabase.createInBackground` を渡せばよい。
`package:loveca_db/native.dart` の `openFileExecutor` は UI isolate 実行なので
**アプリ本体では使わない**（テストと使い捨ての検証向け）。

#### D46: ドラッグは `Draggable` / `DragTarget` で組む。独自実装はしない

★★**掴める領域は「実際に描かれているもの」の上にしか無い。**★★

色も装飾も持たない `Container` / `Row` / `Column` は自分の矩形をヒットテストしない。
そのため行や札の**余白**を押しても `Draggable` まで届かず、ドラッグが始まらない。

実測では、デッキ行の中央を掴もうとして `onDragStarted` が 1 度も呼ばれず、
並べ替え 0/5・削除 0/3 だった。掴ませたい範囲に `color` を与えて
`ColoredBox`（`HitTestBehavior.opaque`）にしたところ **5/5・3/3** になった。

**Phase 3b の盤面でも同じ手当てが要る。** 札の枠・空きスロット・領域の背景を
すべて描画物にしておくこと。怠ると「たまに掴めない」という
再現条件の分かりにくい不具合になる。

★**`ReorderableListView` は採らない。** 行のドラッグを自分で握るため
行を `Draggable` にできず、「並べ替え」と「デッキから外す」を両立できない。
デスクトップでは行末のハンドルからしか掴めず、実測の成功率も 2/5 と低い。
行ごとに `DragTarget` を置く方式なら両立し、3 通りの開始方法すべてで 5/5。

★**`onDragEnd` を当てにしない。** 落下先の処理が元の行を作り直すと呼ばれない
（実測: 開始 5 / 終了 0）。状態の確定は `DragTarget` 側の `onAcceptWithDetails` で行う。

★**タッチ（Phase 5）では `LongPressDraggable` を使う想定で設計する。**
既定の `ImmediateMultiDragGestureRecognizer` はスクロールとジェスチャアリーナを
奪い合うため、タッチではスクロール側が勝ちやすい。
デスクトップでも長押し方式は全操作で成立するので、
入力方式で開始ジェスチャだけ差し替えられる形にしておく。
★**ただしタッチは実機未検証。** Phase 5 の前に確かめ直すこと。

#### D47: 重ね置き（4.5.5）は落下点の局所座標で撃ち分ける

同じスロットに落としても「上に重ねる」と「下に差し込む」を撃ち分けられなければ、
盤面 UI が成立しない。**`Draggable` / `DragTarget` で表現できる。**

- `onMove` / `onAcceptWithDetails` が渡す座標を `RenderBox.globalToLocal` で局所座標へ直す
- スロットの**上半分なら上に重ねる / 下半分なら下に差し込む**
- `onMove` の間、どちらの意味で落ちるかを画面に出す（出さないと利用者は気づけない）

★**`DragTargetDetails.offset` は feedback の左上であってポインタ位置ではない。**
そのままだと「札のどこを掴んだか」で上下判定が変わる。
`dragAnchorStrategy: pointerDragAnchorStrategy` を指定して座標系を揃えること。

最小盤面（メンバーエリア 3 つ・手札・控え室）で、手札→エリア / エリア間移動 /
上に重ねる / 下に差し込む / 控え室へ の 5 操作がすべて成立し、予算超えフレーム 0 だった。

★これは**物理操作の表現**の話であり、4.5.5 の解消などルール上の処理は自動化しない
（D-A / D18）。`docs/PhaseEngine設計メモ.md` の B-3 が定めるのは解消先の判断であって、
この決定はその操作を画面でどう起こすかだけを扱う。

#### D48: 一覧の絞り込みはメモリ上で行う

| 条件 | SQL 再クエリ | メモリ上フィルタ |
|---|---:|---:|
| 商品で絞る | 1〜8 ms | 0.05 ms |
| パラレル表示 OFF（1,727 件） | 10〜14 ms | 0.06〜0.07 ms |

**100〜200 倍速い。** 全 2,527 行はすでにメモリにあるので、絞り込みで DB へ行く理由がない。
両者が同じ件数を返すことは実測で確認済み。

★一覧の取得には**表示に要る列だけを引く**（11〜15 ms）。
既存 DAO で `Card` / `Printing` を全件実体化すると 40〜60 ms かかる。
`CardDao.cardsByNumber()` は `DeckValidator` へ渡すためのもので、一覧表示には重い。

★パラレル表示 OFF は `isParallel == false` の刷りを**すべて**残す（CLAUDE.md §5-(4)）。
cardNumber ごとに 1 枚へ畳まない。



### ★ D49 の詳細（2026-08-23 決定・実装済み）

検索の `trigram` 経路は、索引に入っている**折りたたみ済みの cardNumber** を
保存されている表記へ戻すため、毎回 `SELECT * FROM cards`（1,708 行）を走らせていた。
実測で **trigram 検索 10.13 ms のうち 9.39 ms** がこの復元だった。

**索引に `card_number_raw` を `UNINDEXED` で持たせ、復元処理そのものを無くす。**

| | 復元 | 検索 1 回 | 現行比 |
|---|---:|---:|---:|
| 変更前 | 9.39 ms | 10.13 ms | — |
| **変更後（採用）** | **0（不要）** | **0.74 ms** | **7%** |

代償は索引 **+24 KiB（+2.6%）**。`MATCH` の速さは変わらない（実測 -0.01 ms＝誤差）。

★**`UNINDEXED` にすること。** トークンを作らせると生の表記が検索対象に混ざり、
「索引側とクエリ側の両方に `fold` を通す」という決定 D40 の前提が崩れる。

★**速さ以外の利得のほうが大きい。**
`{fold(cardNumber): cardNumber}` という写像への依存が構造ごと消える。
2 つの cardNumber が同じ値へ畳まれると片方が黙って消える弱点があり、
実データでは衝突 0 件（1,708 → 1,708）だったが、
**これは現時点でそうだというだけで将来の保証ではない。**
`removeFromIndex` も生の値で消すようにしたので、巻き添え削除も起きない。
衝突する cardNumber を人工的に作ったテストで固定してある。

#### ★ 却下した案A（写像をメモリに保持）— 決め手は性能ではない

| | 案A 写像を保持 | 案B 折りたたみ列 + `IN` | **案C（採用）** |
|---|---|---|---|
| 検索 1 回 | 0.76 ms | 1.36 ms | **0.74 ms** |
| 移行 | 不要 | **要**（実テーブル `cards` の列追加） | **要**（索引を建て直すだけ） |
| 状態 | **持つ** | 持たない | 持たない |

**案A は速さでは案C と並んでいた。それでも採らなかった理由は次のとおり。**

`CardSearchDao` は `const` で**呼び出しごとに生成**されるため写像の置き場が無い。
どこかに持たせると、`CardDao` の書き込み（`replaceExpansion` /
`deleteExpansion` / `deleteOrphanCards`）が `CardSearchDao` の写像を
無効化するという逆向きの結合が生まれる。

★**無効化を 1 箇所でも漏らすと「取り込んだ新しいカードが検索で引けない」**
という無言の欠落になる。これは **A-3（数字なし表記を 59 種で無言に落としていた）と
同じ失敗の型**である。
**速さの問題を直すために A-3 型のリスクを新設するのは筋が悪い。**

案B を採らなかったのは、実テーブル `cards` の列追加を伴い移行の失敗が
マスタ本体に及ぶこと、DB 往復と fold 写像への依存が残ることによる。
案C の移行は `card_search` を落として建て直すだけで、
**ユーザデータ（`decks`）に一切触れない**（D11 / D35）。

#### 移行

`schemaVersion` を 2 へ上げ、`MigrationStrategy.onUpgrade` を新設した。
それまで移行の手段が 1 つも無く、スキーマを変えると既存端末のデッキを
捨てるしか手が無い状態だった。**Phase 4 でどのみち要るものの前倒し。**
v1 → v2 は `CardSearchDao.rebuildAll()` 1 本で、
`cards` / `card_names` から索引を建て直す。



### ★ D50 の詳細（2026-08-23 決定・実装済み）

`CardSearchDao.search` の既定は `limit = 500` で、**超過分は戻り値に何の痕跡も
残さず落ちていた。** 実データでの実測は次のとおり。

| 語 | 実際のヒット | 既定（500）での戻り値 |
|---|---:|---:|
| `ー` | **1,034 種** | 500 種（**534 種が無言で欠落**） |
| `ライブ` | **602 種** | 500 種 |

★**呼び出し側は切り捨てを確実には検知できなかった。**
`CardSearchResult` は `cardNumbers` と `mode` しか持たず、
`length == limit` を見るしかないが、これは「ちょうど limit 件だった」場合と
区別がつかない。

**採用: 既定値を 2000 に上げ、かつ切り捨てを戻り値で伝える（併用）。**

| | 上限撤廃 | 既定値変更のみ | **併用（採用）** |
|---|---|---|---|
| 残る問題 | 歯止めが無くなる | **切り捨て時に黙る性質は残る** | 無し |

- 上限そのものは**歯止めとして残す**。撤廃すると、将来データが増えたときに
  呼び出し側が全件を受け取る前提になる
- 既定 2000 は実データの全カード数 1,708 種を上回るので、現状は事実上無制限
- 検出は **`LIMIT n+1` で 1 件多く引く**方式。`COUNT(*)` を別に取ると
  FTS をもう一度引くことになるが、要るのは「上限を超えたか」だけなので 1 件で足りる
- `truncated` が立ったら UI は件数を出す（`CardSearchMode` を UI に出せるように
  してあるのと同じ考え方）

★**A-3 と同じ「無言の欠落」の型である。**
`card_search_dao.dart` は `CardSearchMode.likeFallback` のコメントで
「黙って 0 件を返すのは A-3 と同じ失敗の型なので必ず切り替える」と書きながら、
**同じ関数が `limit` で同じ型の失敗を残していた。** 一貫していなかった。

| | A-3 | `limit: 500` |
|---|---|---|
| 失敗の型 | 痕跡を残さずデータを落とす | **同じ** |
| 起きる時点 | 取り込み時（DB に入らない） | 問い合わせ時（データは DB にある） |
| 可逆性 | 不可逆 | 可逆 |
| 実害 | ブレードハートが 59 種で欠落 | **利用者が「そのカードは無い」と誤解する** |

★**本番の呼び出し元が 0 の今が最も安いタイミングだった。**
`search()` を呼んでいたのはテストだけで、戻り値の型を変えても壊れるものが無かった。
UI 本実装が呼び始めてから直すと呼び出し側の修正が要る。
**同種の「戻り値の形を変える修正」は、呼び出し元が増える前に済ませること。**
