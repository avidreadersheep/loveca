### ★ D36 の詳細（2026-08-23 決定）

巻き戻しの方式として 2 案あった。

| 観点 | 案 A: 履歴に状態変更（逆操作） | **案 B: スナップショット（採用）** |
|---|---|---|
| メモリ | 理屈上は小さい | ★構造共有が効くため差はほぼ無い |
| 実装複雑度 | 全操作に逆操作が要る | pop するだけ |
| 正しさ | 逆操作の網羅が前提。1 つ漏れると静かに壊れる | 構成上正しい |
| 8.4.13 の `firstPlayerId` 復元 | 明示的な逆操作が要る。忘れやすい | 自動 |
| D-A（手動操作）との相性 | 任意の物理操作すべてに逆操作が要る | 影響なし |
| Phase 6 再利用性 | `reduce` のアクションログと二重管理になる | `reduce` と直交 |

**採用理由は 2 点。**

1. **メモリ論拠が構造共有により成立しない。**
   `GameState` / `PlayerState` は `final` + `copyWith` で組まれており、
   未変更の領域リストは参照を共有する。スナップショット 1 件の実費は
   「`GameState` 1 個 + `players` リスト 1 個 + 変更された `PlayerState` 1 個
   + 変更された領域リスト 1 個」に留まる。
2. **案 A は Phase 6 の `reduce` アクションログと二重管理になる。**
   D-D は「Phase 6 の権威サーバが同じ `reduce` / `redact` をコピーゼロで再利用する」と定める。
   `reduce(state, action) -> state` を将来入れるならアクションログはサーバ側の資産であり、
   案 A の差分はそれと重複してどちらが正かが曖昧になる。

#### ★ 静的グラフの逆辺は使えない

8.4.12 が 8.4.9 へ戻るループを持つため、`stepGraph` 上で 8.4.9 の前任は
8.4.8 と 8.4.12 の **2 つ**ある。2 周目の 8.4.9 から 1 つ戻る先は
**1 周目の 8.4.12** であって 8.4.8 ではない。静的には決定できない。
実際に通過した状態の履歴から戻す必要がある。

#### D31 との関係

D31「フェイズを 1 つ戻す」は **ステップ単位に読み替え済み**
（`ルール整合性チェック_v1.06.md` B-1 / 設計メモ §6）。
8.4 が 14 手順の塊のままだと 8.4 の先頭までしか戻れず、機能として使いものにならないため。

D36 はその実装形にあたる。履歴 1 件に `StepCursor` を持たせ、
**「1 ステップ戻す」= カーソルが変わるまで pop** とすることで、
ステップ単位とオペレーション単位の両方を 1 つの機構から取り出す。

- 現在のステップ内で手動操作をしていた場合 → そのステップの**入口**へ着地
- ステップに入った直後の場合 → **1 つ前のステップ**へ着地

D31 の内容は §1 の表に記録してある。


### ★ D37 の詳細（2026-08-23 決定）

`redact` が裏向きのカードを誰から隠すかで、ライブカード置き場と除外領域の扱いが割れる。
**揃えない。**

| 領域 | 秘匿 | 根拠 |
|---|---|---|
| **4.6 ライブカード置き場** | 裏向きを**他プレイヤーからのみ** | 8.2.2 / 8.2.4 |
| **4.13 除外領域** | 裏向きを**全員から** | 4.3.3.2 / 4.13.2 |

**根拠**

**4.3.3.2**「裏向き状態のカードは、カードの情報が書かれている面が見えないように置きます。
**原則として**、裏向きのカードの情報はどのプレイヤーも見ることができません。」

「原則として」の留保が例外を許している。そのうえで 2 つの領域は条文の構造が違う。

- **ライブカード置き場**は 8.2.2 / 8.2.4 により「自身の手札のカードを任意の枚数選んで
  裏向きにライブカード置き場へ置く」——**本人が選んで置く行為**であり、
  本人が内容を知っていることは条文上自明。よってオーナーからは隠さない。
- **除外領域**は 4.13.2 が「特に指示がないかぎり、取り除かれたカードは**表向きに**
  置かれます」と定める。裏向きになるのは効果がそう指示したときだけで、
  **誰が内容を知るかを条文は定めていない**。よって既定の 4.3.3.2 に従い全員から隠す。

**この非対称は条文の構造に由来するものであって実装の都合ではない。**

#### 併せて確定した秘匿の範囲

| 領域 | 秘匿 | 根拠 |
|---|---|---|
| 4.8 メインデッキ置き場 | **全員から**（オーナー含む） | 4.8.2「すべてのプレイヤーに対して非公開領域」 |
| 4.9 エネルギーデッキ置き場 | **全員から** | 4.9.2 同上 |
| 4.11 手札 | 他プレイヤーからのみ | 4.11.2 の明示的な例外 |
| 6.2.1.6 脇置き | 他プレイヤーからのみ | 裏向きだが本人が選んだ |
| 4.5 / 4.7 / 4.10 / 4.12 / 4.14 | 秘匿しない | いずれも公開領域 |

**4.1.2.2** により**枚数は必ず残す**。カードの器は消さず中身だけ差し替える。

#### ★ 秘匿した盤面で集計を走らせないこと

`LiveAggregator` はカードマスタを `cardNumber` で引くため、
秘匿されたカードは**未知カードとして除外**される。
ただし**全件が落ちるわけではない**のが厄介で、メンバーエリア (4.5.3 公開) を読む
8.3.10 は秘匿後も正しい数値を返す一方、ライブカード置き場の裏向きを読む 8.4.2 は
静かに小さい値を返す。**失敗が目立たない。**

→ 集計は必ず秘匿**前**の `GameState` に対して行い、数値だけを配る。
これは権威サーバの設計としても正しい（クライアントに相手のブレード合計を
計算させる根拠が無い）。


### ★ D38 の詳細（2026-08-23 決定）

`ルール整合性チェック_v1.06.md` D-3 に「注釈文はゲームに影響しない。
検索対象から外すか要検討」と未決で記録されていた件。**含める。**

**根拠**

**2.12.4** が定めるのは「注釈文はゲームに影響しない」——すなわち**裁定の射程**である。
検索は裁定ではなく「**紙のカードに印刷されている文字列からカードを見つける**」操作であり、
2.12.4 の射程外にある。除外すると、印刷された文言で引けない**偽陰性**が出る。

**実測（配信データ dataVersion 2 全件）**

| 項目 | 実測 |
|---|---|
| 注釈文を持つカード | **44 種**のみ |
| 効果テキスト総文字数 | 81,064 文字 |
| うち注釈文 | **1,806 文字（2.2%）** |
| 最多の注釈文 | 「（ウェイト状態のメンバーが持つ[ブレード]は、エールで公開する枚数を増やさない。）」25 件 |

含めるコストは索引の 2.2% にすぎず、失う偽陰性のほうが高くつく。

★これは**検索索引にだけ**及ぶ判断であり、`D-A`（カード効果の自動処理をしない）とは無関係。
効果テキストの**構文解析は一切していない**。全文をそのまま索引に入れているだけである。

D-3 の表の当該行は「D38 で解消」に更新済み。


### ★ D39 の詳細（2026-08-23 決定）

`HeartColor.fromKey` / `BladeHeartEffect.fromKey` / `CardType.fromJa` は
未知のキーで `ArgumentError` を投げる。`ルール整合性チェック_v1.06.md` D-1 が
「配信データ駆動アプリとしては、新アイコン追加で既存インストール済みアプリの
マスタロードが全滅する」というリスクを指摘している。

取り込み層（`loveca_db`）でどう扱うかを決める。**商品ファイル単位で隔離する。**

| 案 | 採否 | 理由 |
|---|---|---|
| 全体を fail-fast | ✗ | **D-1 が指摘したリスクそのもの。** 配信データが 1 件でも壊れると既存インストールのマスタロードが全滅する |
| `loveca_core` を寛容化 | ✗ | 禁止事項「`loveca_core` を変更しない」に抵触。**D-1 は判断時期を Phase 4 と定めている** |
| **商品ファイル単位で隔離（採用）** | ○ | 契約の厳格さを保ったまま、アプリが起動不能にならない |

**★D-1 の判断を前倒ししない★**

これは `loveca_db` の取り込み層の運用であって、`fromKey` の契約の変更ではない。
`loveca_core` は 1 文字も変えていない。
**「厳格を維持するか寛容化するか」の本判断は D-1 に残したまま**であり、
Phase 4（認証・同期）で配信経路が固まった時点で改めて決める。

**隔離の中身**

失敗した商品ファイルについて、

1. **ハッシュを `master_files` に記録しない** → `planUpdate` から見て `localHash == null` に
   なり、次回の計画で再取得対象に残る
2. **既存の行を消さない** → 前回取り込めた内容で動き続ける
3. **`import_issues` に `(path, hash, kind, message, 回数)` を記録する**

**★黙って捨てない★**
D-1 は「寛容化するなら『読み飛ばした事実を UI に出す』までを含めること。
黙って捨てるのは A-3 と同じ失敗になる」と釘を刺している。
`MasterStateDao` に `outstandingImportIssueCount()` /
`watchOutstandingImportIssueCount()` / `outstandingImportIssues()` を用意し、
Phase 3b の警告表示から引けるようにした。

「未解消」は **`master_files` に同じ `(path, hash)` が無いこと**で判定する。
取り込みに成功した時点で自動的に未解消から外れるため、手で消す運用にならない
（消し忘れで警告が残り続けるのを防ぐ）。

**★`data_version` を上げる条件★**

`planUpdate` は `remoteVersion.dataVersion <= localDataVersion` で `upToDate` を返す
（`master_data.dart:234`）。1 ファイル失敗したのに `master_state.data_version` を上げると、
次回は `upToDate` になり**失敗したファイルが二度と再取得されない。**
→ **マニフェスト内の全ファイルが揃ったときにだけ更新する。**

据え置きの副作用も検証済み。`planUpdate` は `dataVersion` を**入口の門番にしか
使っておらず**、`filesToDownload` は `localFileHashes` との突き合わせだけで決まる
（`master_data.dart:243-248`）。したがって旧 `data_version` を据え置いても
**全ファイル再取得は起きず、失敗したファイルだけが再取得される。**
`loveca-db/test/master_importer_test.dart` で固定してある。

#### D42: 一覧の画像は `ResizeImage` でセル実寸にデコードする

thumb の原寸は 200x279 で、デコード後は 1 枚 約 218 KiB。

★`cacheWidth` は**物理ピクセル**で指定する。論理 px を渡すと DPR 倍だけ小さくデコードされ、

★**プレースホルダは要る。** 速いスクロール（5,418 px/s）では
2,477 枚中 21〜41 枚しかデコードが間に合わない。
このときフレーム統計は綺麗なままなので、**「フレーム落ちなし」だけを見ると
「空白を高速で流しているだけ」を快適と読み違える。**

★**`precacheImage` の常時先読みは採らない。** 60 セル先読みは速いスクロールでは

### ★ D49 の詳細（2026-08-23 決定・実装済み）

検索の `trigram` 経路は、索引に入っている**折りたたみ済みの cardNumber** を

### ★ D50 の詳細（2026-08-23 決定・実装済み）

`CardSearchDao.search` の既定は `limit = 500` で、**超過分は戻り値に何の痕跡も
残さず落ちていた。** 実データでの実測は次のとおり。

| 語 | 実際のヒット | 既定（500）での戻り値 |
|---|---:|---:|
| `ー` | **1,034 種** | 500 種（**534 種が無言で欠落**） |
| `ライブ` | **602 種** | 500 種 |

★**呼び出し側は切り捨てを確実には検知できなかった。**
`CardSearchResult` は `cardNumbers` と `mode` しか持たず、
`length == limit` を見るしかないが、これは「ちょうど limit 件だった」場合と
区別がつかない。

**採用: 既定値を 2000 に上げ、かつ切り捨てを戻り値で伝える（併用）。**

| | 上限撤廃 | 既定値変更のみ | **併用（採用）** |
|---|---|---|---|
| 残る問題 | 歯止めが無くなる | **切り捨て時に黙る性質は残る** | 無し |

- 上限そのものは**歯止めとして残す**。撤廃すると、将来データが増えたときに
  呼び出し側が全件を受け取る前提になる
- 既定 2000 は実データの全カード数 1,708 種を上回るので、現状は事実上無制限
- 検出は **`LIMIT n+1` で 1 件多く引く**方式。`COUNT(*)` を別に取ると
  FTS をもう一度引くことになるが、要るのは「上限を超えたか」だけなので 1 件で足りる
- `truncated` が立ったら UI は件数を出す（`CardSearchMode` を UI に出せるように
  してあるのと同じ考え方）

★**A-3 と同じ「無言の欠落」の型である。**
`card_search_dao.dart` は `CardSearchMode.likeFallback` のコメントで

|---|---|---|

| 起きる時点 | 取り込み時（DB に入らない） | 問い合わせ時（データは DB にある） |
| 可逆性 | 不可逆 | 可逆 |

★**本番の呼び出し元が 0 の今が最も安いタイミングだった。**
`search()` を呼んでいたのはテストだけで、戻り値の型を変えても壊れるものが無かった。
UI 本実装が呼び始めてから直すと呼び出し側の修正が要る。
**同種の「戻り値の形を変える修正」は、呼び出し元が増える前に済ませること。**
