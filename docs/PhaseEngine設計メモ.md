# B-1. ターンのフェイズ構成

## 1. リーフフェイズは 12 個で確定

根拠は **7.1.2 / 7.3.3 / 8.1.2 の 3 条だけ**で足りる。

```
ターン
├─ 先攻通常フェイズ ────── コンテナ（7.1.2）
│   ├─ アクティブフェイズ      7.4   ← リーフ
│   ├─ エネルギーフェイズ      7.5   ← リーフ
│   ├─ ドローフェイズ          7.6   ← リーフ
│   └─ メインフェイズ          7.7   ← リーフ      （7.3.3）
├─ 後攻通常フェイズ ────── コンテナ（7.1.2）
│   ├─ アクティブフェイズ      7.4   ← リーフ
│   ├─ エネルギーフェイズ      7.5   ← リーフ
│   ├─ ドローフェイズ          7.6   ← リーフ
│   └─ メインフェイズ          7.7   ← リーフ      （7.3.3）
└─ ライブフェイズ ──────── コンテナ（7.1.2 / 7.8）
    ├─ ライブカードセットフェイズ  8.2   ← リーフ
    ├─ 先攻パフォーマンスフェイズ  8.3   ← リーフ
    ├─ 後攻パフォーマンスフェイズ  8.3   ← リーフ
    └─ ライブ勝敗判定フェイズ      8.4   ← リーフ  （8.1.2）
```

**4 + 4 + 4 = 12。**

### コンテナとリーフを分ける条文上の根拠

- **7.3.1**「通常フェイズとは、いずれかのプレイヤーが一連のフェイズを実行する**総合的なフェイズ**です」
  → 通常フェイズがコンテナであることは条文が明示している。
- **8.3.1**「パフォーマンスフェイズとは、いずれかのプレイヤーがライブの一連の**処理**を実行するフェイズです」
  → 「総合的な」の語が無く、下位は「フェイズ」ではなく「処理」。8.3.3〜8.3.17 は手順であって
  下位フェイズではない。よって**パフォーマンスフェイズはリーフ**。
- **8.3.2.1** により、先攻/後攻パフォーマンスフェイズは同じ 8.3 の手続きの 2 インスタンス。
  8.1.2 も後攻パフォーマンスフェイズにだけ節番号を振らず、8.3 を再利用することを示している。

### ★「13 フェイズ」は誤記

**引き継ぎドキュメントおよび CLAUDE.md §8 の「13 フェイズ」は誤り。**
条文に 13 番目に相当するフェイズは存在せず、「13」という数はルール本文のどこにも現れない。
7.1.2 / 7.3.3 / 8.1.2 のいずれも過不足なく列挙しており、解釈の余地は無い。

なお「フェイズ」と名の付く語の総数を数えると、リーフ 12 + コンテナ 3 = 15 になる。
**12 と 15 はありえるが、13 はありえない。**

## 2. 8.4.13 / 8.4.14 をフェイズに昇格させない

### 決定

条文上、8.4.13（先攻入れ替え）と 8.4.14（ターン終了）は
**ライブ勝敗判定フェイズ 8.4 の第 13・第 14 手順**であって、フェイズではない。
これを 13 個目のフェイズにする当初提案は**誤りとして撤回する。**

### 理由

1. **8.1.2 がライブフェイズの中身を 4 つと明示している。**
   5 つ目を足すと条番号とフェイズの 1 対 1 対応が崩れ、
   CLAUDE.md §1「ルールに触れるコードには条番号を併記する」が守れなくなる。

2. **条文はターン境界の誘発を意図的に既存フェイズへ畳み込んでいる。**

   | 誘発 | 条文上の発生位置 | 属するフェイズ |
   |---|---|---|
   | 「ターンの始めに」 | 7.4.2 | アクティブフェイズ |
   | 「ターンの終わりに」 | 8.4.10 | ライブ勝敗判定フェイズ |

   `turnEnd` フェイズを作ると「ターンの終わりに」の置き場所が 8.4.10 と `turnEnd` の
   2 箇所に見え、誘発の置き違いを招く。ターン開始側に対応するフェイズが無いことからも、
   条文がこの畳み込みを意図していることが読み取れる。

3. **8.4.11 の期限切れ効果の消滅も 8.4 の内部。**
   8.4.12 は **8.4.9 へ戻るループ**を持つため、`turnEnd` を切り出すと
   ループ範囲とフェイズ境界が交差する。

### 受け皿はステップ層が持つ

| 決定 | 受け皿 |
|---|---|
| D25「先攻入れ替えは手動確定した勝敗をもとに自動適用」 | **ステップ 8.4.13**（先攻入れ替えの単一停止点） |
| D31「フェイズを 1 つ戻すで代用」 | **ステップ単位の巻き戻し**（§6） |

## 3. フェイズはロールで定義する（★実プレイヤー ID を埋めない）

### 決定

**8.4.13 で先攻・後攻が入れ替わるため、フェイズ定義に実プレイヤー ID を持たせてはいけない。**

- フェイズ名はロール（**先攻 / 後攻 / ロールなし**）で定義する
- 実プレイヤーは `GameState` の `firstPlayerId` から実行時に解決する
- `firstPlayerId` を書き換える場所は **8.4.13 の 1 箇所だけ**

フェイズが「先攻通常フェイズ」であることはターンを跨いで不変だが、
そこに座る実プレイヤーはターンごとに変わりうる。両者を混ぜると、
入れ替えの起きたターンで全フェイズの手番が誤る。

### 手番プレイヤーの有無で 2 種類に割れる（7.2）

7.2.1.1 / 7.2.1.2 が定めるアクティブプレイヤーの決まり方が、リーフによって違う。

| リーフフェイズ | 手番プレイヤー | アクティブプレイヤー | 条番号 |
|---|---|---|---|
| 先攻通常フェイズ配下 4 個 | 先攻 | 手番プレイヤー | 7.3.2 / 7.3.2.1 / 7.2.1.1 |
| 後攻通常フェイズ配下 4 個 | 後攻 | 手番プレイヤー | 7.3.2 / 7.3.2.1 / 7.2.1.1 |
| 先攻パフォーマンスフェイズ | 先攻 | 手番プレイヤー | 8.3.2 / 8.3.2.1 / 7.2.1.1 |
| 後攻パフォーマンスフェイズ | 後攻 | 手番プレイヤー | 8.3.2 / 8.3.2.1 / 7.2.1.1 |
| ライブカードセットフェイズ | **なし** | **先攻プレイヤー** | 8.2.2 / 8.2.4 が両者、**7.2.1.2** |
| ライブ勝敗判定フェイズ | **なし** | **先攻プレイヤー** | 8.4.2 以降が両者、**7.2.1.2** |

→ **手番あり 10 個 / 手番なし 2 個。**

アクティブプレイヤーを参照する箇所（すべて `firstPlayerId` に依存する）:

| 参照元 | 内容 |
|---|---|
| 1.3.4 | 複数プレイヤーが同時に選択する場合、アクティブプレイヤーから先に選択 |
| 1.3.4.2 | 非公開領域の同時選択もアクティブプレイヤーが先 |
| 9.5.3.2 / 9.5.3.3 | チェックタイミングでの待機自動能力のプレイ順 |
| 10.2.4 | 両者同時リフレッシュは**現ターンの先攻**が先 |

## 4. ステップ層の定義

ステップ ID は**条番号そのもの**。`(リーフフェイズ, 条番号)` で一意になる。
節番号を持たない定義条（8.3.1 / 8.3.2 など）はステップにしない。

凡例: **CT** = チェックタイミング（9.5.1 / 9.5.3）

#### ★ 8.4 で実装を誤りやすい 3 点

1. **8.4.4（ライブ成功の事象）は 8.4.6（勝敗決定）より前にある。**
   「ライブ成功」はライブカード置き場にカードが残っていれば発生し、
   ライブに勝ったかどうかとは**独立**。11.6.2 も 8.4.4 を参照している。

2. **8.4.13 が参照するのは 8.4.6 の勝敗ではなく、8.4.7 で実際に移動したかどうか。**
   8.4.7.1 により「両者勝利かつライブ置き場に 2 枚あるプレイヤー」は移動しない。
   したがって **勝敗 ≠ 移動**。8.4.6 の結果で先攻を入れ替えると誤る。
   → 8.4.7 の**移動実績**を記録してから 8.4.13 で参照する。

3. **8.4.2 と 8.4.3 と 8.4.6 は別物。**
   8.4.2 は合計、8.4.3 は比較の**規約定義**、実際の比較と勝者決定は 8.4.6。

## 5. 分岐とループをステップ層でどう表現するか

ステップ列を単純な配列にせず、**各ステップが後続候補を持つ有向グラフ**にする。
ほとんどのステップは後続が 1 つだが、以下の 2 箇所だけ 2 つ持つ。

| 分岐点 | 後続候補 | 条番号 |
|---|---|---|
| **8.3.6** | 8.3.7 へ進む **または** パフォーマンスフェイズを終了 | 8.3.6 |
| **8.4.12** | **8.4.9 へ戻る** **または** 8.4.13 へ進む | 8.4.12 |

### 分岐条件の判定主体は同じではない

CLAUDE.md §1「カード効果の自動処理は実装しない」との整合を、分岐ごとに切り分ける。
判定に**効果テキストの解釈が要るか**が境界になる。

| 分岐 | 条件の性質 | 判定の主体 |
|---|---|---|
| **8.3.6** | 盤面の観測のみ（ライブカード置き場が空か） | **アプリが自動判定してよい** |
| **8.4.7.1** | 盤面の観測のみ（両者勝利かつライブ置き場に 2 枚） | 自動判定可。ただし D10 の手動確定の結果に従属 |
| **8.4.12** | **自動能力の誘発有無を含む**（8.4.11 の CT で自動能力やルール処理が解決されたか、未誘発の「ターンの終わりに」等があるか） | **プレイヤーが宣言する** |

8.4.12 の条件は「まだ誘発すべき自動能力が残っているか」を問うており、
これはカードテキストの解釈そのもの。アプリが判定してはいけない。
**「まだ処理がある / 無い」をプレイヤーが選ぶ 2 択**として提示する。

### 8.3.6 の早期終了で飛ばす範囲

8.3.6 で終了した場合、**8.3.7 から 8.3.17 までを丸ごと飛ばす**。
このとき **11.5.2.1** により「ライブ開始時」（8.3.8）の事象は**発生しない**。
早期終了を「8.3.17 へジャンプ」と実装すると 8.3.17 の CT が余分に走るので、
フェイズ終了へ直接遷移させる。

### リフレッシュはステップ境界を無視する

**10.2.1**「リフレッシュはチェックタイミングにかぎらず、ゲーム中の任意の時点で（中略）
それがなんらかの処理の途中である場合、その処理を一時中断し、リフレッシュを実行した後に、
その処理の続きを実行します」

→ 8.3.11 のエール（メインデッキの一番上を N 回移動）の**途中**でデッキが尽きた場合、
その場でリフレッシュし、残り回数を続行する。
他のルール処理（10.1.2 は CT でのみ実行）と挙動が違うので、**実装場所を分ける**。

- 10.2.2.1: メインデッキが空で控え室にカードがある場合
- 10.2.2.2: 「上から見る」の指示枚数にメインデッキが足りない場合
- 10.2.3: 控え室を非公開にしてシャッフルし、メインデッキの**下**へ差し込む
- 10.2.4: 両者同時なら**現ターンの先攻**が先 → `firstPlayerId` を参照

## 6. D31「フェイズを 1 つ戻す」はステップ単位で実装する

### 決定

**巻き戻しの単位はフェイズではなくステップ。**
8.4 が 14 手順の塊のままだと 8.4 の先頭までしか戻れず、巻き戻し機能として使いものにならない。

### ★ 静的なグラフの逆辺をたどってはいけない

**8.4.12 が 8.4.9 へ戻るループを持つため、「1 つ前のステップ」は静的なグラフから決まらない。**

```
8.4.9 → 8.4.10 → 8.4.11 → 8.4.12 ─┐
  ↑                                 │
  └─────────────────────────────────┘   （8.4.12 → 8.4.9）
```

2 周目の 8.4.9 から 1 つ戻る先は、**1 周目の 8.4.12** であって 8.4.8 ではない。
グラフ上 8.4.9 の前任は 8.4.8 と 8.4.12 の 2 つあり、静的には決定できない。

→ **実際に通過したステップの履歴スタックを保持し、そこから戻す。**

### ターン境界を跨ぐ巻き戻し

8.4.13 は `firstPlayerId` を書き換える唯一のステップ。
ターン境界を跨いで戻す場合、**書き換え前の `firstPlayerId` も履歴から復元する**必要がある。

### ★ 方式の確定（2026-08-23 / 決定 D36）

かつてここは「ステップ履歴に状態変更を持たせるか、ステップ境界ごとの GameState
スナップショットを持つかは Phase 3a の実装判断」と**未決**にしていた。
**スナップショット（案 B）で確定する。**

| 観点 | 案 A: 履歴に状態変更（逆操作） | **案 B: スナップショット（採用）** |
|---|---|---|
| メモリ | 理屈上は小さい | ★`GameState` が完全にイミュータブルなので**構造共有が効く**。差はほぼ無い |
| 実装複雑度 | 全操作に逆操作が要る | pop するだけ |
| 正しさ | 逆操作の網羅が前提。1 つ漏れると**静かに壊れる** | 構成上正しい |
| 8.4.13 の `firstPlayerId` 復元 | 明示的な逆操作が要る。**忘れやすい** | 自動 |
| D-A（手動操作）との相性 | 移動 / 反転 / 回転 / 重ね置きなど**任意の物理操作すべて**に逆操作が要る | 影響なし |
| Phase 6 再利用性 | 差分は同期向きだが `reduce` のアクションログと**二重管理**になる | `reduce` と直交 |

**決め手は 2 点。**

1. **メモリ論拠が成立しない。** 案 A を選ぶ主な理由はメモリ効率だが、
   `GameState` / `PlayerState` が `final` + `copyWith` で組まれているため
   スナップショットは既に構造共有されている。1 件の実費は
   「`GameState` 1 個 + `players` リスト 1 個 + 変更された `PlayerState` 1 個
   + 変更された領域リスト 1 個」で、残りは参照を共有する。
2. **Phase 6 と二重管理になる。** CLAUDE.md §1（D-D）は
   「Phase 6 の権威サーバが同じ `reduce` / `redact` をコピーゼロで再利用する」と書く。
   `reduce(state, action) → state` を将来入れるならアクションログはサーバ側の資産になる。
   案 A の差分はそれと重複し、どちらが正かが曖昧になる。

### 巻き戻しの粒度

履歴 1 件に `StepCursor` を持たせ、**「1 ステップ戻す」= カーソルが変わるまで pop** とする。
これで**ステップ単位とオペレーション単位の両方**を 1 つの機構から取り出せる。

- 現在のステップ内で手動操作をしていた場合 → そのステップの**入口**へ着地する
- ステップに入った直後の場合 → **1 つ前のステップ**へ着地する

D31「フェイズを 1 つ戻す」は §6 冒頭のとおり**ステップ単位に読み替え済み**であり、
この粒度がその実装形になる。

実装は `loveca-core/lib/src/game/history.dart`。

## 7. 前提（4.5.5）

ver 1.06 でメンバーの下に**メンバーカードも**置けるようになった。

### ★ 4.5.5.2 の帰結

下のカードは**アクティブ / ウェイトの概念を持たない**。したがって、

## 8. 解消の分岐表（★核心）

最初の分岐は「**移動先がメンバーエリアかどうか**」。カード種別による分岐はその後。

| # | 条件 | 挙動 | 条番号 |
|---|---|---|---|
| 1 | メンバーが**他のメンバーエリア**へ移動 | 下のカードも重なったまま**同時に移動**（解消しない） | **4.5.5.3** |
| 2 | メンバーが**メンバーエリア以外**へ移動 | **メンバーカードのみが移動**。下のカードは取り残される | **4.5.5.4** |

| 2-b | 取り残されたのが**エネルギーカード** | エリアに残留 → ルール処理で**エネルギーデッキ置き場**へ | **4.5.5.4.2 → 10.5.4** |

**エネルギーカードは控え室を経由しない閉ループ**である。

### ★ 即時には消えない — 「孤児カード」は正規の中間状態

4.5.5.4.1 / 4.5.5.4.2 はいずれも

**10.1.2**「ルール処理は、リフレッシュ（10.2）を除き、**チェックタイミングにおいてのみ**
条件を満たしているかを確認し、満たされている場合に実行されます」

→ 上のメンバーが去ってから次のチェックタイミングまでの間、
**「上にメンバーが居ない孤児カードがメンバーエリアに存在する」状態が正規に存在する。**

GameState はこの状態を表現できなければならない。

## 9. 10.5.5 の解釈（決定: 広義）

**10.5.5**「上記のいずれかの処理において、控え室に置くカードがエネルギーカードである場合、
それを控え室に置くのではなく、エネルギーデッキ置き場に置きます。」

「上記のいずれか」の範囲が条文上あいまい。**広義（10.3〜10.5 全体）**と読む。
根拠は、条文が最初からエネルギーカードを**閉ループ**として設計している点にある。

### 主根拠: エネルギーカードは控え室を経由しない閉ループとして設計されている

エネルギーカードの動線を条文どおりに追うと、控え室に一度も触れない閉じた輪になる。

| 遷移 | 条番号 |
|---|---|
| ゲーム開始時、エネルギーデッキ置き場に置く | 4.9.1 / 6.2.1.3 |
| エネルギーデッキ置き場 → エネルギー置き場 | 6.2.1.7（開始時 3 枚）/ 7.5.2（毎ターン 1 枚） |
| エネルギー置き場の中でアクティブ ⇄ ウェイト（コストの支払い） | **5.9.1（領域を移動しない）** |
| エネルギー置き場 → メンバーの下 | 5.10.1 → 4.5.5 |
| メンバーの下 → エネルギーデッキ置き場 | 4.5.5.4.2 → 10.5.4 |

- **5.9.1 のコスト支払いはウェイトにするだけで、カードは領域を移動しない。**
  使用済みエネルギーが控え室へ落ちる仕組みがそもそも存在しない。
- **6.1.1.1** によりメインデッキはメンバー 48 枚 + ライブ 12 枚。エネルギーは含まれない。
  したがってエネルギーが手札・メインデッキ・控え室の側の循環（10.2 リフレッシュ）に
  合流する経路も無い。
- **条文全体を通して「エネルギーカードを控え室に置く」と書いた条は 1 つも存在しない。**
  本文中でエネルギーと控え室が同じ条に現れるのは 10.5.2 と 10.5.5 の 2 つだけで、
  10.5.2 は「エネルギー置き場のエネルギー**でない**カード」を控え室へ送る**逆向き**の規定。

→ **6.1.1.3 のエネルギーデッキ 12 枚は、ゲーム中のどの時点でも
エネルギーデッキ置き場・エネルギー置き場・メンバーの下のいずれかにある。**

### 10.4.1 が、その閉ループを破る唯一の例外を作る

10.5.1〜10.5.4 はいずれも対象をカード種別で名指ししている。
これに対し **10.4.1（重複メンバー処理）だけが「カード」としか言わない。**

> 「最も後から置かれたメンバーを 1 枚選び、**それ以外のそのメンバーエリアのカード**を
> オーナーの控え室に置きます」

メンバーエリアには 4.5.5 によりエネルギーカードが重ねられている。
種別に触れない書き方のため、**メンバーの下のエネルギーカードが控え室へ巻き込まれる。**
これが閉ループを破る唯一の経路になっている。

### 10.5.5 はその例外を塞ぐ規定

閉ループが設計として先にあり、10.4.1 がそれを破りうるので、10.5.5 が行き先を差し戻す。
この読みでのみ 10.5.5 は明確な仕事を持つ。

→ **「上記のいずれか」は 10.5 節の内部に閉じず、10.3〜10.5 の全体を指す。**

### 補助根拠: 狭義に読むと規定がほぼ空振りする

「上記のいずれか」を 10.5.1〜10.5.4 に限定すると、10.5.5 が適用される場面がほとんど無い。
規定が無意味になる読みは採らない。

| 条 | 対象 | 10.5.5 が効くか |
|---|---|---|
| 10.5.1 | ライブカード置き場のライブでない表向きカード | メインデッキにエネルギーは入らない（6.1.1.1）ため通常発生しない |
| 10.5.2 | エネルギー置き場の**エネルギーでない**カード | 定義上エネルギーではない → 効かない |
| 10.5.3 | 上にメンバーの無い**メンバーカード** | 定義上エネルギーではない → 効かない |
| 10.5.4 | 上にメンバーの無い**エネルギーカード** | すでにエネルギーデッキ行き → 不要 |

### 決定と不変条件

**10.5.5 は 10.3〜10.5 の全体に適用する（広義）。**

→ 不変条件: **ルール処理でエネルギーカードが控え室へ行く経路は存在しない。**

カード効果が明示的にエネルギーを控え室へ送る場合は別（効果は手動処理なので、
アプリはこれを禁止しない）。よって「控え室にエネルギーがある」ことを
ハードな不変条件にはせず、**ルール処理経由でそうなったときだけ警告**する。

| 10.1.2 | リフレッシュ（10.2）を除き、ルール処理は**チェックタイミングでのみ**判定・実行 |
| 10.1.3 | ルール処理が複数同時に求められる場合、**すべて同時に実行** |
| 9.5.3.1 | 実行後に新たなルール処理が生じていれば、無くなるまで繰り返す |

→ **1 回の「整理」= 現在成立している 10.3〜10.6 を同時実行 → 再判定、のループ。**

ルール処理の判定は**原則として効果テキストの解析を伴わない盤面の観測だけ**で完結するため、
自動化しても CLAUDE.md §1「カード効果の自動処理は実装しない」には抵触しない。
**ただし 10.3 と 10.6 は例外**で、どちらも自動実行してはいけない（下表）。

| ルール処理 | 内容 | 整理コマンドで自動実行してよいか |
|---|---|---|
| 10.3 勝利処理 | 成功ライブカードが 3 枚以上 | **不可（警告のみ）。D10 に従う** |
| 10.4 重複メンバー処理 | 1 エリアに複数メンバー | 可（§10 の【要確認】に従う） |
| 10.5 不正カード処理 | 10.5.1〜10.5.5 | 可 |
| **10.6 不正解決領域処理** | 解決領域に処理中でないカード | **不可（警告のみ）** ★訂正 |

### 10.3（勝利処理）を自動実行しない理由

**D10「勝敗確定は手動ボタン」と競合する。**
なお 1.2.1.2 により**両者同時に 3 枚以上なら引き分け**なので、D10 の手動確定には
引き分けの選択肢が要る。整理コマンドは該当を**検出して警告する**に留め、盤面を触らない。

### ★ 10.6（不正解決領域処理）を自動実行しない理由 — 訂正（2026-08-23）

**当初この表は 10.6 を「可」としていたが誤り。10.3 と同じく「不可（警告のみ）」に訂正する。**

> **10.6.1**「解決領域に現在**プレイ中または解決中である**またはエール処理中（8.3.11）で
> ある以外のカードが存在する場合、ルール処理として、そのカードをオーナーの控え室に置きます。」

**「プレイ中 / 解決中」の判定には効果の解決状態の管理が要り、D-A に抵触する。**
「エール処理中」はカーソルから観測できるが、「プレイ中 / 解決中」は 9.6 のプレイと解決の
進行状況そのものであり、効果の自動処理を実装しない以上アプリは知りようがない。

さらに悪いことに、**D-A のもとでプレイヤーは効果を手動処理するために解決領域へカードを置く。**
アプリが「プレイ中でも解決中でもエール処理中でもない」と判定して自動で控え室へ送ると、
**プレイヤーが進行中の作業を破壊する**。誤検出の代償が大きすぎる。

→ 10.3 と同様、**該当を検出して警告する**に留め、送るかどうかはプレイヤーが判断する。

## 12. Phase 3a への申し送り

6. リフレッシュ（10.2）はステップ境界を無視して割り込む。CT 内のルール処理とは
   実装場所を分ける。
