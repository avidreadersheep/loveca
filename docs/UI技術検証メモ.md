## 1. 環境と土台

### 1-1. Windows デスクトップビルドは通る

`flutter doctor -v` の実測。

| 項目 | 値 |
|---|---|
| Flutter / Dart | 3.41.4 stable / 3.11.1 |
| Visual Studio | **Community 2026 18.4.11605.240（C++ デスクトップ開発ワークロード検出済み）** |
| Windows SDK | 10.0.26100.0 |
| デバイス | `Windows (desktop) • windows • windows-x64` |

**追加インストールは要らない。**

### 1-2. `sqlite3` はビルドフックのまま Flutter でも動く。`sqlite3_flutter_libs` は採らない

`loveca_db` は `sqlite3` 3.5.2 のビルドフック（native assets）で SQLite 本体を自前調達している。
Flutter 経路でも同じ仕組みが働くことを実測で確かめた。

| 確認 | 結果 |
|---|---|
| Flutter の native assets | stable で既定有効（`flutter_tools/lib/src/features.dart` の `nativeAssets` が `enabledByDefault: true`） |
| ビルド成果物 | `build/windows/x64/runner/Debug/sqlite3.dll` が実際にバンドルされる |
| 解決された SQLite | **3.53.4 / FTS5 あり / trigram あり** |
| 別 isolate から | `NativeDatabase.createInBackground` 経由で `card_search`（FTS5 仮想テーブル）を引けた |
| 実データ | 1,708 種 / 2,527 刷り / 検索索引 1,708。`failedPaths` `unhandledPaths` とも空 |
| thumb の WebP | 200x279 にデコードできる（ファイル 19,010 B → デコード後 約 218 KiB） |

★**`sqlite3_flutter_libs` を足さないこと。** 足すと SQLite が二重に調達され、
実行時にどちらを掴んだのか分からなくなる。FTS5 の有無が環境依存に戻る。

★**初回ビルドはネットワークを使う。** ビルドフックの既定は
GitHub リリースから `sqlite3.dll` を**ダウンロード**する経路
（`sqlite3/lib/src/hook/compile/description.dart` の `PrecompiledFromGithubAssets`）。
調達物はパッケージごとにキャッシュされるので、`loveca-db` で取得済みでも
`loveca-ui` の初回ビルドでは取り直しになる。

### 1-3. ★`display.refreshRate` の報告値を信じてはいけない

この環境の `display.refreshRate` は **60.0 Hz と報告する**が、
実際には **144Hz 前後**でフレームが出ている（vsync 開始時刻の間隔の中央値から算出）。

報告値を予算にすると 1 フレーム 16.7 ms となり、**実際の予算 6.9 ms の 2.4 倍**ゆるくなる。
最初この誤りのまま測っていて、すべての条件が「予算超え 0 件」に見えていた。
実測値に直したところ §3-2 の差がはじめて現れた。

**フレーム予算は観測値から求めること。** 実装は
[`spike/common/metrics.dart`](../loveca-ui/spike/common/metrics.dart) の `_observedPeriodUs`。

## 3. 試作1 — 仮想リスト

測定条件: 2,527 セル / セル幅 **120 物理 px**（thumb の原寸は 200x279）/ 実測 144Hz・予算 6.9 ms。

★★**2026-08-24 追記: 「thumb の原寸 200x279」はメンバーの値であって全種ではない。**★★
M5 で thumb 2,527 枚を全数計測したところ、**ライブは 200×143 の横長**だった
（メンバー 200×279/280、エネルギー 200×279/280/273、ライブ 200×143/144）。
上の測定はセルを 200:279 固定で敷き詰めた条件のものであり、**その条件自体は変わっていない**
（一覧はいまも全セル 200:279）。詳細は `docs/UI設計メモ.md` §5-1 / §9-9 / 未決 U11。
スクロールは端から端まで等速で流す。全域 43,347 px。

- **fling**: 8 秒（**5,418 px/s**）— 指ではじいた勢い
- **browse**: 40 秒（**1,084 px/s**）— 眺めながら送る速度

### 3-1. `GridView.builder` の仮想化自体は問題ない

画像を出さない条件（グリッド自体のコスト）で、fling / browse とも
build p50 0.3〜0.4 ms、予算超え 0〜3 フレーム（0.1%）。**2,527 セルでも一覧の骨組みは十分に軽い。**

### 3-2. ★`ResizeImage` が要る。無いと実際にフレームが落ちる

browse（実際に全 2,477 枚がデコードされる速度）での比較。

| 条件 | 予算超え | raster max |
|---|---:|---:|
| `Image.file` 既定（200px でデコード） | **25 フレーム (0.4%)** | 8.2 ms |
| **`+ ResizeImage`（セル実寸 120px でデコード）** | **0 フレーム** | 6.0 ms |
| `+ ResizeImage + imageCache 256MiB` | 5 (0.1%) | 33.2 ms |
| `+ ResizeImage + プレースホルダ` | **0 フレーム** | 6.4 ms |
| `+ ResizeImage + precacheImage 60 セル先読み` | 0 フレーム | 5.4 ms |

**`cacheWidth` は物理ピクセルで指定する。** 論理 px を渡すと DPR 倍だけ小さくデコードされ、
拡大表示になってぼやける。

### 3-3. 画像キャッシュの上限は既定のままでよい

各パス終了時点のキャッシュ。Flutter の既定は **1000 枚 / 100 MiB**。

| 条件 | キャッシュ枚数 | キャッシュ量 | RSS ピーク |
|---|---:|---:|---:|
| `Image.file` 既定（1 枚 約 207 KB） | **500 枚** | **99.9 MiB** | 182 MiB |
| `+ ResizeImage`（1 枚 約 74 KB） | **1000 枚** | 72.5 MiB | 190 MiB |
| `+ ResizeImage + 256MiB` | 1000 枚 | 72.5 MiB | 187 MiB |

既定のままだと**バイト上限が先に効いて 500 枚で追い出しが始まる**。
`ResizeImage` を入れると 1 枚あたりが約 1/2.8 になり、**枚数上限（1000 枚）側が先に効く**。
つまり **27% 少ないメモリで 2 倍の枚数が載る。**

★**`maximumSizeBytes` を引き上げても何も増えない**（1000 枚 / 72.5 MiB で頭打ち）。
上限を触るのではなく `ResizeImage` で 1 枚を小さくするのが正しい手当て。

### 3-4. ★速いスクロールではデコードが追いつかない。プレースホルダは要る

「フレーム落ちが無い」だけでは判断できないので、**実際に絵が出た枚数**を数えた。

| 速度 | 絵が出た枚数（全 2,477 枚中） |
|---|---:|
| fling（5,418 px/s） | **21〜41 枚**（1〜2%） |
| browse（1,084 px/s） | 2,477 枚（100%） |

fling ではほぼ何も間に合っていないのに、フレーム統計は綺麗に出る。
**空白を高速で流しているだけの状態を「快適」と読み違えないこと。**

プレースホルダ無しだと、その間セルは何も描かれない（透明）。
**カード大の下地を必ず置く。** 追加コストは測定範囲では見えなかった（予算超え 0）。

### 3-5. `precacheImage` の先読みは常時採らない

可視範囲の 60 セル先まで先読みする条件では、fling 速度だと
**8 秒で全 2,477 枚を読み切ってしまう**（キャッシュ命中 2,477 / 絵が出た 0）。
60 セル先読みは、この速度では実質「全件先読み」になる。

- 効果: すべてのセルが即座に描ける
- 代償: **RSS ピークが 175〜178 MiB（先読み無しは 141〜151 MiB）**

★**常時有効にはしない。** 採るなら「スクロールが止まっている間だけ」「可視範囲の 1〜2 画面分だけ」
のように条件を絞る。上限の無い先読みはメモリを食うだけになる。

### 3-6. フィルタはメモリ上で絞る

| 条件 | SQL 再クエリ | メモリ上フィルタ | 件数 |
|---|---:|---:|---:|
| 商品 BP01 のみ | 1〜8 ms | 0.05 ms | 180 |
| コスト 2 以下 | 2 ms | 0.03〜0.05 ms | 208 |
| パラレル表示 OFF | 10〜14 ms | 0.06〜0.07 ms | **1,727** |
| 商品 + コスト 3 以下 | 0 ms | 0.04〜0.08 ms | 12 |

**100〜200 倍速い。** 全 2,527 行はすでにメモリにあるので、絞り込みで DB へ行く理由がない。
どちらも同じ件数になることは実測で確認済み（表の「件数」は両者一致）。

★パラレル表示 OFF は `isParallel == false` の刷りを**すべて**残す（CLAUDE.md §5-(4)）。
cardNumber ごとに 1 枚へ畳まない。

## 4. 試作2 — 検索の応答性

### 4-1. ★`search()` の時間の大半は FTS ではない

`CardSearchDao.search` を 1 回呼んだときの内訳（各 5 回の中央値・別 isolate）。

| 語 | 経路 | search() 全体 | うち FTS の MATCH | うち `cards` 全件読み |
|---|---|---:|---:|---:|
| 花帆（2 文字） | likeFallback | 1.02 ms | — | — |
| スクール（4 文字） | trigram | 11.03 ms | 0.62 ms | **10.51 ms** |
| ブレード（4 文字） | trigram | 12.59 ms | 1.20 ms | **9.77 ms** |
| ライブ（3 文字） | trigram | 14.98 ms | 1.85 ms | **8.67 ms** |

**FTS5 の MATCH 自体は 0.3〜1.9 ms。残りは索引に入っている折りたたみ済み cardNumber を
元の表記へ戻すための `SELECT * FROM cards`（1,708 行）で、これが毎回走っている**
（`loveca-db/lib/src/search/card_search_dao.dart` の `_resolveCardNumbers`）。

結果として **2 文字以下の `LIKE` 全走査（0.5〜2.3 ms）のほうが trigram より速い**という
逆転が起きている。

★**この試作では `loveca_db` を変更していない。** 同じ SQL をこちら側から投げて
内訳を測っただけ。改善案は §9 に「変更提案」として分けて置く。

### 4-2. 刷りへの展開は無視できる

検索結果は cardNumber なので刷りへ広げる必要がある（呼び出し側の責務）。
実測 **0.00〜0.13 ms**。設計上の考慮は要らない。

### 4-3. ★デバウンスは打鍵間隔を超えないと 1 回も減らない

「スクールアイドル」（8 文字）を一定間隔で入力したときの実測（別 isolate）。

**打鍵間隔 120 ms**

| デバウンス | 実行された検索 | うち無駄 | DB 合計 | 最後の打鍵から結果まで |
|---:|---:|---:|---:|---:|
| 0 ms | 8 回 | 7 回 | 157.8 ms | **24 ms** |
| 50 ms | 8 回 | 7 回 | 170.1 ms | 78 ms |
| 100 ms | **8 回** | 7 回 | 152.7 ms | **128 ms** |
| **150 ms** | **1 回** | 0 回 | **28.2 ms** | 179 ms |
| 250 ms | 1 回 | 0 回 | 36.3 ms | 288 ms |

**打鍵間隔 60 ms**

| デバウンス | 実行された検索 | うち無駄 | DB 合計 | 最後の打鍵から結果まで |
|---:|---:|---:|---:|---:|
| 0 ms | 8 回 | 7 回 | 145.2 ms | 25 ms |
| 50 ms | **8 回** | 7 回 | 138.1 ms | **76 ms** |
| **100 ms** | **1 回** | 0 回 | 26.7 ms | 128 ms |
| 150 ms | 1 回 | 0 回 | 28.2 ms | 179 ms |

★**デバウンス値が打鍵間隔以下だと、検索回数は 1 回も減らないまま待ち時間だけが増える。**
打鍵 120 ms のときデバウンス 100 ms は、8 回検索したうえで待ち時間を 24 ms → 128 ms にする。
**純粋に損。**

**採用値は 150 ms。** 理由は 2 つ。

1. 日本語入力は IME の変換確定を挟むため、実際の `onChanged` 間隔は
   ローマ字 1 文字ごと（60〜120 ms 相当）になる。150 ms なら両方の速度で 1 回に畳める
2. 179 ms は人が「引っかかった」と感じる 200 ms を下回る

### 4-4. 結果件数は描画の制約にならない。上限は「黙って切らない」ためだけに要る

| 語 | limit | 種 | 刷り | 検索 | 結果を描くまで | 予算超え |
|---|---:|---:|---:|---:|---:|---:|
| ー | 500 | 500 | 804 | 1.57 ms | 8 ms | 0 |
| ー | 1000 | 1000 | **1,623** | 2.51 ms | 10 ms | 0 |
| ー | 1708 | 1,034 | **1,668** | 1.88 ms | 7 ms | 0 |
| ライブ | 500 | 500 | 822 | 23.05 ms | 4 ms | 0 |
| ライブ | 1708 | 602 | 1,015 | 15.00 ms | 4 ms | 0 |

**1,668 刷りでも描画は 4〜10 ms で予算超え 0。** `GridView.builder` が仮想化しているので、
件数は描画コストにほとんど効かない。**描画都合の上限は要らない。**

★問題は別にある。**現在の既定 `limit: 500` は結果を黙って切る。**
`ー` は実際には 1,034 種、`ライブ` は 602 種ヒットするのに、既定だと 500 で打ち切られ、
利用者にはそれが分からない。これは CLAUDE.md が繰り返し戒めている
「黙って 0 件」（`CardSearchMode.likeFallback` のコメント）と同じ型の失敗。

**上限は 2000 に上げ**（実データの最大が 1,708 種なので事実上の無制限）、
**それでも打ち切られたときは件数を画面に出す。**

## 5. drift の executor は別 isolate にする

同じ試作を `--dart-define=LOVECA_DB_BACKGROUND=false`（UI isolate）でも走らせて比べた。

| 観点 | UI isolate | **別 isolate（採用）** |
|---|---|---|
| trigram 検索 1 回 | **7.8〜9.3 ms** | 11.0〜15.0 ms |
| `LIKE` 検索 1 回 | **0.5〜0.9 ms** | 0.9〜2.3 ms |
| 打鍵中の予算超えフレーム | 2/41 が発生 | 0 |
| **コールド取り込み中に出たフレーム** | **26 フレーム / 1,285 ms（約 20fps）** | **242 フレーム / 1,800 ms** |

検索 1 回だけを見ると UI isolate のほうが速い（isolate 間の往復が無いぶん）。
**しかし決め手はコールド起動の取り込み。** 1.8 秒の取り込みが UI スレッドで走ると
画面はほぼ止まる（20fps）。別 isolate なら止まらない。

`loveca_db` は `LovecaDatabase(QueryExecutor)` という形で executor を呼び出し側から
受け取る設計になっているので、**`loveca_db` を変更せずに**アプリ側で

```dart
LovecaDatabase(NativeDatabase.createInBackground(File(path)))
```

と組み立てればよい。`package:loveca_db/native.dart` の `openFileExecutor` は
UI isolate 実行なので、**アプリ本体では使わない**（テストと使い捨ての検証向け）。

## 6. 試作3 — ドラッグ操作

### 6-1. ★★ 掴める領域は「実際に描かれているもの」の上にしか無い ★★

**これが今回いちばん重要な発見。**

色も装飾も持たない `Container` / `Row` / `Column` は、自分の矩形をヒットテストしない。
そのため行や札の**余白**（テキスト行の隙間など）を押しても `Draggable` まで届かず、
**ドラッグがそもそも始まらない。**

実測では、デッキ行の中央を掴もうとして **`onDragStarted` が 1 度も呼ばれなかった**。

| | 修正前 | 修正後 |
|---|---:|---:|
| デッキ内の並べ替え | **0 / 5** | **5 / 5** |
| デッキ → 削除 | **0 / 3** | **3 / 3** |

掴む点の真下をヒットテストで出すと、原因がはっきりする。

```
修正前: RenderMetaData < RenderPointerListener < ...   ← 行の中身に当たっていない
修正後: _RenderColoredBox < RenderPointerListener < RenderMetaData < ...
```

**手当ては単純**で、掴ませたい範囲に `color` を与えて `ColoredBox`
（`HitTestBehavior.opaque`）にする。`Material` でも `GestureDetector(behavior: opaque)` でもよい。

★**Phase 3b の盤面でも同じ手当てが要る。** 札の枠・空きスロット・領域の背景は
すべて「描かれている」状態にしておくこと。これを怠ると
「たまに掴めない / たまに落とせない」という、再現条件の分かりにくい不具合になる。

診断のためのヒットテスト経路の出力は
[`spike/common/pointer_driver.dart`](../loveca-ui/spike/common/pointer_driver.dart) の `hitTestAt` に残してある。

### 6-2. `ReorderableListView` は採らない

| 方式 | 並べ替え | 掴める場所 | 領域外への持ち出し |
|---|---:|---|---|
| `ReorderableListView` | **2 / 5** | デスクトップでは**行末のハンドルだけ** | **できない**（行を `Draggable` にできない） |
| **行ごとに `DragTarget`（採用）** | **5 / 5** | 行のどこでも | できる（3 / 3） |

`ReorderableListView` は行のドラッグを自分で握るため、同じ行を掴んでゴミ箱へ引き出す操作が作れない。
デッキ編集では「並べ替え」と「デッキから外す」を同じ行で両立させたいので、この時点で外れる。
実測の成功率も低い（掴める帯が狭い）。

### 6-3. ★重ね置き（4.5.5）は `Draggable` / `DragTarget` で表現できる

同じスロットに落としても「上に重ねる」と「下に差し込む」を撃ち分けられるかが核心だった。
**撃ち分けられる。**

- `DragTarget` の `onMove` / `onAcceptWithDetails` が渡す座標を
  `RenderBox.globalToLocal` で局所座標へ直す
- スロットの**上半分なら上に重ねる / 下半分なら下に差し込む**
- `onMove` の間、どちらの意味で落ちるかを帯で出す（出さないと利用者は気づけない）

★**`DragTargetDetails.offset` は feedback の左上であってポインタ位置ではない。**
そのままだと「札のどこを掴んだか」で上下判定が変わってしまう。
`dragAnchorStrategy: pointerDragAnchorStrategy` を指定して
ポインタ位置と feedback の左上を揃えること。

### 6-4. ドラッグの開始方法

| 方式 | リスト→デッキ（横） | 並べ替え（縦・一覧の中） | 持ち出し（縦） |
|---|---:|---:|---:|
| `Draggable` 既定（即時） | 6 / 6 | 5 / 5 | 3 / 3 |
| `LongPressDraggable` | 6 / 6 | 5 / 5 | 3 / 3 |
| `Draggable(affinity: horizontal)` | 6 / 6 | 5 / 5 | 3 / 3 |

§6-1 を直したあとは、**デスクトップ（マウス）では 3 方式とも成立する**。
デスクトップは既定（即時）でよい。タッチの事情は §7-2。

### 6-5. feedback の作り方はコストに効かない

カード画像を feedback にした場合と単色の箱にした場合で、フレーム統計に差は出なかった
（どちらも予算超え 0 / raster max 1.7〜2.1 ms）。**見栄えで選んでよい。**

### 6-6. `onDragEnd` は当てにしない

落下先の処理が元の行を作り直すと（並べ替え・削除など）、
**`onDragEnd` が呼ばれない**（実測: 開始 5 / 終了 0）。
後始末を `onDragEnd` に置かないこと。状態の確定は `DragTarget` 側の `onAcceptWithDetails` で行う。

## 7. Phase 3b への転用可否 — **可**

### 7-1. 盤面の物理操作は同じ部品で成立する

メンバーエリア 3 つ・手札・控え室を持つ最小盤面で、合成ポインタを流して実測。

| 操作 | 結果 |
|---|---|
| 手札 → メンバーエリア | ○ |
| メンバーエリア間の移動 | ○ |
| 重ね置き / 上に重ねる | ○ |
| **重ね置き / 下に差し込む（4.5.5）** | **○** |
| メンバーエリア → 控え室 | ○ |

フレーム統計は予算超え 0（build p50 0.1 ms / raster p50 0.8 ms）。

**独自のドラッグ実装（`Listener` + `Overlay` を自前で組む）は要らない。**
`Draggable` / `DragTarget` に足りなかったのは「落下点の局所座標」だけで、
それは `onMove` / `onAcceptWithDetails` から取れる。

★ただし前提が 2 つある。**どちらも守らないと成立しない。**

1. 掴む対象・落とす対象を**必ず描画物にする**（§6-1）
2. `dragAnchorStrategy: pointerDragAnchorStrategy` で座標系を揃える（§6-3）

### 7-2. タッチ環境（Phase 5）の所見 — ★実機では未検証

今回のビルドは **Windows デスクトップのみ**。以下は API と実装から論じた所見であり、
**実機・エミュレータでの確認はしていない。**

- `Draggable` の既定は `ImmediateMultiDragGestureRecognizer`。
  スクロールできる領域の内側では、スクロールとジェスチャアリーナを奪い合う
- マウスでは競合が起きにくいが、**タッチでは同じ縦方向の指の動きが
  スクロールとドラッグのどちらにも解釈できる**ため、スクロール側が勝ちやすい
- そのため Flutter は一覧の中の並べ替えに `ReorderableDelayedDragStartListener`（長押し起点）を
  既定にしている
- **タッチでは `LongPressDraggable` を使う想定で設計しておくのが妥当**。
  §6-4 のとおりデスクトップでも長押し方式は全操作で成立するので、
  **同じコードのまま入力方式で開始ジェスチャだけ差し替えられる**形にしておく

★盤面（Phase 3b）は PC 専用（CLAUDE.md 冒頭の表）なので、
タッチが要るのはデッキ構築側だけ。**Phase 5 に入る前に実機で確かめ直すこと。**

## 9. `loveca_db` の検索コスト（★決定 D49 / D50 として実装済み）

★**当初は提示に留めていたが、その後 決定 D49 / D50 として実装済み。**
以下は判断に使った測定と対比をそのまま残したもの。
数値は `spike/main_search_variants.dart` の実測（`06_search_variants.md`）。
`loveca_db` は変更せず、現行と同じ SQL をこちら側から投げ、
別案は「その案なら走るはずの処理」を同じデータへ走らせて比べた。

### 9-0. 前提: `fold` は cardNumber 上で単射（衝突 0 件）

`_resolveCardNumbers` は `{fold(cardNumber): cardNumber}` を作るため、
2 つの cardNumber が同じ値へ畳まれると**片方が黙って消える**。
実データで確認したところ **1,708 種 → 折りたたみ後 1,708 種・衝突 0 件**。

★**現時点で成立しているだけで、将来の保証ではない。**
新商品の cardNumber が既存と全角半角違いだけで衝突すると、静かに引けなくなる。
案 A / B はこの写像に乗り続け、案 C は写像そのものが不要になる。

### 9-1. `_resolveCardNumbers` の全件読み

trigram 経路の 70〜90% が `SELECT * FROM cards`（1,708 行）だった（§4-1）。
3 案を同じデータで測った結果。

| | 復元の中央値 | 検索 1 回の合計 | 現行比 |
|---|---:|---:|---:|
| 現行 | 9.39 ms | **10.13 ms** | — |
| 案A 写像を保持 | 0.02 ms | **0.76 ms** | 7% |
| 案B 折りたたみ列 + `IN` | 0.62 ms | **1.36 ms** | 13% |
| 案C 索引に生値を持つ | 0（復元が要らない） | **0.74 ms** | 7% |

案C の代償（メモリ上に同じ 1,708 種で索引を建てて比較）。

| 索引 | 大きさ | MATCH |
|---|---:|---:|
| 現行（5 列） | 0.89 MiB | 0.20 ms |
| 案C（+ `card_number_raw UNINDEXED`） | 0.91 MiB | 0.18 ms |
| 差 | **+24 KiB (+2.6%)** | 変わらず（誤差） |

#### 対比

| | 案A 写像を保持 | 案B 折りたたみ列 + `IN` | **案C 索引に生値**（推奨） |
|---|---|---|---|
| **(1) 変更範囲** | スキーマ変更なし。ただし `CardSearchDao` は `const` で**呼び出しごとに生成**されるため写像の置き場が無く、DAO のライフサイクル設計を変える必要がある | **実テーブル `cards` に列 + 索引**。`schemaVersion` 1→2 と `onUpgrade` 新設。列の backfill が要る | **仮想テーブル `card_search` の列追加**。`schemaVersion` 1→2 と `onUpgrade` 新設。移行は落として建て直して再索引 |
| **移行の要否** | 不要 | **要**（実テーブル） | **要**（ただし `cards` / `card_names` からの純粋な派生物なので作り直すだけ。ユーザデータに触れない） |
| **(2) 改善見込み** | 10.13 → **0.76 ms（7%）** | 10.13 → **1.36 ms（13%）** | 10.13 → **0.74 ms（7%）** |
| **(3) 副作用とリスク** | ★**無効化漏れが静かな不整合になる。** `CardDao` の書き込み（`replaceExpansion` / `deleteExpansion` / `deleteOrphanCards`）が `CardSearchDao` の写像を無効化する逆方向の結合が生まれる。1 箇所漏らすと「取り込んだ新カードが検索で引けない」。**A-3 と同じ失敗の型を新設することになる** | 冗長列が 1 つ増える（`fold` を変えたら再生成が要る。`cards.search_blob` と同じ手当てが 2 列に増える）。DB 往復は残る。fold 写像への依存も残る | 索引 +2.6%（+24 KiB）。「索引には fold 済みだけを入れる」という現在の設計思想から外れるので理由をコメントに残す必要。**`_resolveCardNumbers` が消え、fold 衝突リスク（9-0）も同時に消える** |
| **(4) Phase 4（同期）** | 影響なし（同期対象は `decks`。`cards` / `card_search` は dist からの派生でローカル専用） | 同左。ただし `schemaVersion` を上げるため移行機構の新設が先行する | 同左 |
| **(4) Phase 6（権威サーバ）** | ★プロセス内状態を持つため、複数プロセスで各自が保持し、マスタ更新の伝播を考える必要が出る | 影響なし（DB に閉じる） | 影響なし（DB に閉じる） |

★**3 案に共通の前提**: 現在 `MigrationStrategy` に **`onUpgrade` が無い**
（`schemaVersion` は 1 で `onCreate` と `beforeOpen` のみ）。
案B / 案C はどちらも「移行機構そのものの新設」が最初の作業になる。
これは Phase 4 でどのみち要るものなので、前倒しになるだけで無駄にはならない。

#### 推奨: 案C → **決定 D49 として採用・実装済み**

1. 最速タイ（現行の 7%）でありながら、案A と違い**状態を持たない**
2. **`_resolveCardNumbers` という処理自体が消える。** 性能だけでなく
   9-0 の衝突リスクも同時に無くなる
3. **移行が最も安全。** `card_search` は `cards` / `card_names` からの純粋な派生物なので
   落として建て直すだけで、ユーザデータ（`decks`）に一切触れない。
   案B は実テーブル `cards` の列追加で、移行の失敗がマスタ本体に及ぶ
4. 代償が実測で小さい（索引 +24 KiB・MATCH は変わらず）

★**案A を採らない決め手は性能ではない。**
性能は案C と並ぶが、`CardDao` の書き込みが `CardSearchDao` の写像を無効化する
という結合を作る点が悪い。無効化を 1 箇所漏らすと
「取り込んだ新カードが検索で引けない」という無言の欠落になる。
**性能問題を直すために A-3 型のリスクを新設するのは筋が悪い。**

### 9-2. ★`limit: 500` が結果を黙って切っている（実バグ → **決定 D50 で解消**）

**(a) 事実**

`CardSearchDao.search` の既定は `limit = 500` で、超過分は戻り値に何の痕跡も残さず落ちる。

| 語 | 実際のヒット | 既定（500）での戻り値 |
|---|---:|---:|
| `ー` | **1,034 種** | 500 種 |
| `ライブ` | **602 種** | 500 種 |

**(b) 呼び出し側が検知できるか — 確実にはできない**

`CardSearchResult` は `cardNumbers` と `mode` しか持たない。総数も打ち切りフラグも無い。
呼び出し側は自分が渡した `limit` と `length` を比べるしかないが、

- `length == limit` は「ちょうど limit 件だった」と区別がつかない（**偽陽性**）
- trigram 経路は `_resolveCardNumbers` が写像に無い値を落とすため、
  SQL 側が切られていても `length < limit` になりうる（**偽陰性**）。
  fold 衝突が 0 件の現在は起きないが、構造上は起こりうる

**(c) 修正方針の対比**

| | 上限撤廃 | 既定値変更（500→2000） | **戻り値で通知**（併用を推奨） |
|---|---|---|---|
| 挙動 | `LIMIT` を外す | 実データ最大 1,708 種を上回るので事実上無制限 | `LIMIT n+1` で 1 件多く引き、超えたら `truncated` を立てる |
| 描画への影響 | 問題なし（1,668 刷りで 4〜10 ms・予算超え 0 / §4-4） | 同左 | 同左 |
| 残る問題 | **歯止めが無くなる。** 将来データが増えたときに呼び出し側が全件を受け取る前提になる | **打ち切りが起きたときに黙る性質は残る**（起きにくくなるだけ） | 無し |
| コスト | 小 | 小 | 小（`COUNT(*)` を別に取る必要はない） |

**推奨は「既定値変更 + 戻り値で通知」の併用。** 上限は歯止めとして残す。
→ **決定 D50 として採用・実装済み**（`defaultLimit = 2000` / `CardSearchResult.truncated`）。

★**今が最も安い。** `search()` の**本番の呼び出し元は現時点で 0**（テストのみ）。
戻り値の型を変えても壊れるものが無い。UI 本実装が呼び始めてから直すと呼び出し側の修正が要る。

**A-3 と同じ「無言の欠落」の型か — 該当する（ただし A-3 より軽い）**

| | A-3 | `limit: 500` |
|---|---|---|
| 失敗の型 | 出力に痕跡を残さずデータを落とす | **同じ** |
| 呼び出し側が損失を知る手段 | 無い | **確実には無い**（(b)） |
| 起きる時点 | **取り込み時**。DB に入らない | 問い合わせ時。データは DB にある |
| 可逆性 | 不可逆（再取り込みが要る） | 可逆（`limit` を上げれば取れる） |
| 実害 | ブレードハートが 59 種で欠落 | 検索結果の後ろが出ない＝**利用者が「そのカードは無い」と誤解する** |

★同じファイルの同じ関数が、`CardSearchMode.likeFallback` のコメントで
「黙って 0 件を返すのは A-3 と同じ失敗の型なので必ず切り替える」と書きながら、
`limit` では同じ型の失敗を残している。**一貫していない。**
