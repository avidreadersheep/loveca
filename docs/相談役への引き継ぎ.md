## 1. 何を作っているか

ラブライブ！シリーズ オフィシャルカードゲーム（通称「ラブカ」）の
**非公式シミュレーター**。個人利用・非商用。

```
カードを検索できる → デッキを作れる → ソロで回せる → オンラインで対戦できる
```

★★**アプリはルールエンジンではない。**★★
効果の自動解決・誘発の自動発動・効果テキストの構文解析は**一切しない**（**D-A**）。
紙と同じようにプレイヤーが判断し、アプリは**物理操作のサンドボックス**を提供する
（引く / シャッフル / 移動 / 上から見る / 反転 / 横向き / 重ね置き / 選択）。
★**この一線がほぼすべての設計判断の上流にある。**「自動でやってくれないのは手抜きでは」
という指摘は、ここを覆す提案として扱う必要がある。

### 盤面のモードは 3 つ（決定 **D88**）

| モード | 領域 | 秘匿 | 手番 |
|---|---|---|---|
| **ソロ** | 自分側のみ | `redact` を掛けない（隠す相手が居ない） | 常に先攻 |
| **ローカル対戦** | 両側 | `redact` を掛けない（1 人が両方を操作する） | 8.4.13 で入れ替わる |
| **オンライン対戦**（Phase 6・未着手） | 両側 | サーバが `redact` を掛けて配る | 同上 |

★**ソロとローカル対戦は「秘匿しない理由」が違う。**
理由が違うものを「どちらも隠さない」と 1 行にまとめない、というのがこのプロジェクトの書き方。

★★**「一人回し」という語は廃止された。**★★
D88 以前の文書・コミットに出てくる「一人回し」は**すべてローカル対戦**を指す。
同じ語が時期によって別の意味になると `grep` で新旧を区別できないため。
廃止を記録する 3 文書（`CLAUDE.md` / `docs/決定事項一覧.md` / `docs/盤面設計メモ.md`）以外に

## 4. このプロジェクトで確立された原則

★★**どれも「そう決めた」ではなく「実際に踏んで学んだ」ものである。**★★
実例を 1 つずつ添える。

### 4-1. D-A —— カード効果の自動処理は実装しない

> **実例**: ライブ成功判定（8.3.15 / 8.3.16）を自動化しない（**D18**）。
> 集計は数値を出すところまでで、満たすかの判断はプレイヤーがする。
> ★**同じ原則から「10.6 のルール処理を実行しない」も導かれている** ——
> 「プレイ中 / 解決中」は効果の解決状態であり、アプリは観測できないため。

★**この原則は「実装が条文より広い」ことを許す。**
紙ならライブカードをメンバーの下に置けるので、実装も禁じない（**D95**）。
条文が定めていない状態には**ルール処理を適用しない**ことで整合させる。

### 4-2. D-B —— 根拠のない値をコードに書かない

> **実例**: 脇置き（6.2.1.6）の落とし先を盤面に置かない（**D93-2**）。
> 置けば操作経路は 1 つ増えるが、**6.2.1.6 の外で脇置きに札が残る**という
> **条文が定めていない状態**を実装が作れてしまう。
> ★**3 つの文書がこれを「利点」として書いていた**のを訂正した。

★**例外は「利用者が指定した」ことである**（**D97**）。
既定のエネルギーカードは条文にも実データにも根拠が無い（実データ上ゲーム上の差が 1 件も無い）。
★**D-B が禁じるのは「根拠のない値」であって「利用者が決めた値」ではない。**

### 4-3. D-10 —— 検知手段は、見つかるはずのものを仕込んで動かす

> **実例**: `.gitignore` の未アンカー規則が本実装のファイル群を隠していた。
> ★**すべての検出手段が正常を報告した** —— `git status` は clean、テストは全通過、
> アナライザは指摘なし、実機は起動する。**異常はクローンした先にしか現れない。**

★★**結論: 0 件は「無い」と「見えていない」の区別がつかない。**★★
このプロジェクトのテストは**必ず対（陽性対照）を持つ**——§4-5 参照。

### 4-4. D-15 —— 列挙による断定は黙って古くなる

> **実例**: 「参照透過でないのは乱数を消費する 3 つだけ」というコメントが、
> ★**書かれた時点で既に実装と食い違っていた**（4 つ目が間接的に消費していた）。
> 以後 (a)〜(l) まで同じ型が繰り返し出ている。

★**型は 1 つではない**（正は `ルール整合性チェック_v1.06.md` D-15）——
実装が動いて doc が古くなる型 / doc が**最初から実装より広い**型（走査で出ない）/
doc が**誤った方針**を書く型 / **検証していない完了報告**（実機で押すまで出ない）/
**実行できない確認予定** / ★**未実装の決定の前提を、別の決定が動かしていた**型。

★★**規約は 3 つ。**★★
(1) 数を書くなら**機械が数えられる形**にする (2) 数える手段が無い断定は**テストで固定するか書かない**
(3) ★**同じ数を 2 箇所に書かない**。
★**どちらを消すかは「もう 1 つの側が文書か、機械で数えられるものか」で決まる** ——
文書なら数を消し、コードなら消さずに直す。

★**「正はあちら」と書き添えるだけでは足りない**ことが実測されている。数がそこにある限り古くなる。

### 4-5. 陽性対照 —— 「出る側」だけのテストは何も証明しない

> **実例**: 整理で盤面の札が消えないことを固定する不変条件を置いたとき、
> ★**本体を測る前に「走査を盲目にしたら落ちること」を先に確かめた。**
> 走査自体が見えていないなら、常に通ってしまうため。

★同じ作法が随所にある —— ドラッグの手当ては**外すと落ちる**ことを実測してある。
検索の縮退は「起きる入力で出ること」と「起きない入力で出ないこと」を**対で**固定してある。
★**出る側だけを見ると「常に出す実装」でも通る。**

★★**対を置いたら、対象を壊して対が落ちることを実測すること**（**D-27** / 2026-08-27 追加）。★★
★**置いただけの対は飾りである** —— 実例では、対が掴んでいたのが
**区分の見出し**であって縮退の帯ではなく、**縮退を丸ごと殺しても通っていた。**
`findsOneWidget` は「誰が出したか」を見ないので、**同じ状況で出る別の文字列**を掴んでいても
字面からは分からない。★**入れ子は 1 段で止まる**（対象を壊して落ちれば、その対は対象を見ている）。

★★**契機を 2 つ足した**（**D-27** / ★2026-09-02 追加。★★上の 5 行は 1 文字も書き換えない★★）。★★
★**分類（甲 / 乙）だけでは足りなかった** —— ★**作法にした★★同じ回に 2 回踏んだ★★**（★相談役の判定）。
★**足りなかったのは分類ではなく★★「いつ当てるか」★★である。**

★★引く機会が来ない限り引かれない★★。★契機は★★書いた瞬間に必ず来る★★。**

### 4-6. 根拠の格を分ける

> **実例**: 盤面の最小幅（**D83**）。
> (a) 外部標準（Material の閾値）は**存在しない**と確かめた /

> (b-3) 可読性は**別の定数の話**であって窓幅の話ではない。
> ★**格の違う根拠を並べて 1 つの数字にしない。**

★★**ただし、この格の表記には精度の軸が無い**（**D-28** / 2026-08-27 追加）。★★

→ ★★**実測値を正として記録するなら、刻み幅・標本点・判定手段を併記する。**★★
★**「〜付近」と書いた値は下限ではない**（嘘ではないが、引用されるときに「付近」が落ちる）。

### 4-7. 条文の記述と実装判断を混ぜない

★**混ぜて「条文どおりだから直せない」と読ませない。**

### 4-8. 「1 コミット = 1 論点」
